# 🤝 Contributing to OpenSetup

First of all, thank you for your interest in contributing to **OpenSetup**!

Whether you're submitting a new setup guide, improving an existing one, fixing bugs, enhancing the UI, or proposing new features, every contribution helps make OpenSetup a better resource for developers.

---

# 📖 Before You Begin

Before contributing, please:

- Read through this guide completely.
- Search existing Issues before creating a new one.
- Follow the project's coding standards and best practices.
- Keep contributions focused and meaningful.

---

# 📝 Contributing a Setup Guide

The easiest way to contribute is directly through the **Contribute** page on OpenSetup.

Fill out the submission form with the following details.

| Field | Description | Example |
|--------|-------------|---------|
| **File Name** | A short, URL-friendly filename without spaces. Keep it concise and descriptive. | `vite-react-ts` |
| **Full Title** | The complete title of your guide. | `Vite + React + TypeScript` |
| **One-Line Description** | A short summary explaining what the guide covers. | `Guide to set up React using Vite with a TypeScript environment.` |
| **Category** | Select the primary technology category. | `Frontend` |
| **Category Type** | Select the type of guide. | `SCAFFOLD` |
| **Guide Content** | Upload a Markdown file or write the guide directly in the built-in editor. | `setup.md` |

---

## 📂 Available Categories

Currently supported categories are:

- Frontend
- Backend
- Fullstack
- Devops

---

## 🏷️ Available Category Types

Choose the category type that best describes your guide.

| Type | Purpose |
|------|---------|
| **SCAFFOLD** | Creating a new project or application from scratch. |
| **INTEGRATION** | Connecting services, APIs, libraries, or third-party tools. |
| **CONFIG** | Configuration files, tooling, environments, or project setup. |
| **DOTFILES** | Personal development environments, terminal setups, editor configurations, and dotfiles. |

---

# 📄 Guide Format

Before writing your guide, download and review the provided **`setup_template.md`**.

The template demonstrates the expected structure, formatting style, writing quality, and level of detail expected for every guide submitted to OpenSetup.

Following the template significantly increases the chances of your guide being approved.

---

# ✅ Review Process

After submitting your guide:

1. Your submission enters the review queue.
2. An administrator reviews the guide.
3. The guide is evaluated for:
   
   - Accuracy
   - Clarity
   - Completeness
   - Formatting
   - Overall usefulness
     
5. If the guide meets the project's quality standards, it will be published.
6. If improvements are required, the submission may be rejected along with a reason explaining what should be improved.

The goal is to maintain a consistently high-quality collection of setup guides for the community.

---

# 💡 Improving OpenSetup

Contributions are not limited to setup guides.

If you'd like to improve OpenSetup itself, you're welcome to contribute by:

- Fixing bugs
- Improving existing guides
- Enhancing the user interface
- Adding new features
- Improving performance
- Refactoring code
- Improving documentation
- Suggesting new guide categories
- Suggesting new guide types

For larger changes, please create an Issue first so the feature or enhancement can be discussed before implementation.

If the proposal aligns with the project's direction and is worth pursuing, it will be assigned for development.

---

# 💻 Coding Standards

OpenSetup follows modern development practices to keep the codebase clean, maintainable, and scalable.

When contributing code, please ensure that you:

- Write clean and readable code.
- Follow existing project architecture.
- Use meaningful variable and function names.
- Keep components modular and reusable.
- Maintain consistent formatting.
- Avoid unnecessary complexity.
- Preserve TypeScript type safety.
- Write responsive UI where applicable.
- Follow the existing folder structure.
- Keep pull requests focused on a single improvement whenever possible.

Please match the existing coding style and best practices used throughout the project.

---

# 🚀 Pull Requests

Before opening a Pull Request, make sure you have:

- Forked the repository.
- Created a new branch for your changes.
- Tested your changes locally.
- Ensured there are no build or linting issues.
- Written a clear Pull Request description explaining your changes.
